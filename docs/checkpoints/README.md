# Checkpoint Notes

Checkpoint notes capture one accepted visual-review pass at a time.

Older notes in this folder predate the polish overlay and should be read as valid history, not as incomplete failures.

Current delivery status is recorded in the
[September 30 Blueprint integration receipt](2026-09-30-blueprint-integration.md).
Use the [active roadmap](../source-backed-next-thread-roadmap.md) for priorities;
historical receipts keep their original claims.

## Default Structure

Each checkpoint note should include:

- `Goal`
- `What changed`
- `What visibly improved`
- `What still feels weak`
- `What the compare pack caught`
- `Next swing`

## Polish-Heavy Pass Overlay

If the pass is primarily about typography, spacing, hierarchy, shell framing, top-fold presentation, or other taste-heavy polish, add these lines:

- `Why This Was Accepted`
- `What Was Intentionally Left Alone`

These lines should stay short. The goal is to preserve acceptance reasoning without turning the checkpoint into a design essay.

## Related Review Inputs

For polish-heavy passes, the checkpoint should be readable alongside:

- the compare report in `.codex-tmp/visual-review/latest/`
- the Polish Intent Card from the current review pass

If a pass was invisible maintenance only, skip the overlay and do not force a visual checkpoint just to satisfy the format.
